Análisis Arquitectónico del Proyecto

Visión General y Patrón Arquitectónico

El proyecto utiliza un patrón de Microservicios (Microservices Architecture) respaldado por el principio "Database-per-Service" (una base de datos aislada por cada servicio). Todo está contenerizado usando Docker y Docker Compose, operando sobre una red virtual privada llamada pad-network para garantizar que los microservicios no expongan sus puertos directamente al exterior.

Capa de Presentación (Frontend)

  • Tecnología: Angular 21 (Single Page Application - SPA).
  • Servidor Web: Nginx, que se encarga de servir los archivos estáticos en el puerto 80.
  • Seguridad: El frontend no se comunica directamente con las bases de datos ni con los microservicios internos. Todas las peticiones HTTP/REST pasan obligatoriamente por el API Gateway usando un token JWT en las cabeceras.

Puerta de Enlace (API Gateway)

  • Tecnología: Spring Cloud Gateway (Java 17).
  • Puerto: 8080.

Funciones Core:

  • Punto de entrada único: Intercepta todo el tráfico que viene del Frontend.
  • Seguridad Perimetral: Se encarga de validar la firma de los tokens JWT (HS256). Si el token es válido, enruta la petición al microservicio correspondiente; si no, la bloquea.
  • Manejo estricto de políticas CORS.

Ecosistema de Microservicios (Backend)

Desarrollados en Java 17 con Spring Boot 3.x. El sistema está dividido en 6 dominios de negocio (Bounded Contexts):

  • Servicio de Estudiantes (Puerto 8082): El "corazón" de la identidad. Gestiona usuarios, perfiles, matrículas, apoderados, permisos de retiro y fichas médicas (Health Records).
  • Servicio de Cursos (Puerto 8083): Administra la estructura curricular (niveles, grados, secciones), asignaturas, infraestructura física (aulas) y cruce de horarios para docentes.
  • Servicio de Evaluaciones (Puerto 8084): Gestiona las calificaciones según los estándares del MINEDU (escala literal AD, A, B, C) y controla el registro de asistencias diario por bloque horario.
  • Servicio de Disciplina (Puerto 8081): Un módulo de convivencia escolar que registra incidentes, méritos y emite papeletas disciplinarias.
  • Servicio de Reportes (Puerto 8085): Es un servicio agregador. Como las bases de datos están separadas, este servicio hace peticiones HTTP internas (usando Feign o WebClient) a los otros servicios para juntar datos y generar boletines estadísticos consolidados.
  • Servicio de Notificaciones (Puerto 8086): Un consumidor de eventos asíncronos que envía alertas, correos, SMS o mensajes de WhatsApp sin bloquear las operaciones principales del sistema.

Capa de Persistencia e Integridad (Bases de Datos)

  • Motor: PostgreSQL 15.
  • Para no levantar 6 contenedores pesados de base de datos, se levanta 1 solo clúster (Contenedor pad-postgres), pero internamente se crean bases de datos lógicas totalmente aisladas (academico_estudiantes, academico_cursos, academico_evaluaciones, etc.).
  • Soft Foreign Keys: Como no se pueden hacer JOINs tradicionales entre diferentes bases de datos, el sistema usa "Llaves foráneas suaves". La integridad referencial se valida mediante lógica de negocio en Java y rutinas de reconciliación.
  • Acceso y Gestión: Se incluye un contenedor con pgAdmin 4 (puerto 5050) para que los administradores técnicos inspeccionen las tablas.

Mensajería y Eventos (Message Broker)

  • Tecnología: RabbitMQ (Protocolo AMQP en el puerto 5672).
  • Cuando un docente emite una papeleta disciplinaria o se ingresa una nota crítica, en lugar de esperar a que se envíe el correo (lo cual hace lenta la app), el servicio emite un mensaje a una cola en RabbitMQ. El Servicio de Notificaciones lee esta cola en segundo plano y envía el correo/SMS.

Observabilidad y Monitoreo (Opcional/Perfil)

El proyecto cuenta con un stack de grado empresarial para evitar operar "a ciegas":

  • Prometheus (9090): Extrae ('scrapea') métricas de memoria, CPU y uso de los microservicios Spring Boot.
  • Grafana (3000): Paneles visuales hermosos para leer los datos de Prometheus.
  • Zipkin (9411): Distributed Tracing. Como una petición del Frontend puede pasar por el Gateway, luego a Reportes, y luego a Cursos, Zipkin rastrea exactamente por dónde pasó la petición y cuánto milisegundos tardó en cada salto, facilitando encontrar "cuellos de botella".

Resumen de Calidad del Diseño

Es una arquitectura altamente robusta, diseñada para alta escalabilidad y tolerancia a fallos. La segregación de roles (MATRIZ_ROLES.md), la contenerización y el uso de mensajería asíncrona demuestran que es un proyecto preparado para despliegues reales en la nube (AWS/GCP/Azure) o en centros de datos educativos pesados.
