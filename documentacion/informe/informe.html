    Introducción

    Un colegio público de Educación Secundaria gestiona cada día información crítica: la matrícula de cientos de estudiantes, la asignación de la carga horaria a los docentes, la asistencia de ingreso y de aula, las calificaciones por competencias, la convivencia escolar, la salud y el bienestar de los estudiantes y la comunicación con las familias. En la mayoría de instituciones estos procesos se llevan en cuadernos, hojas de cálculo aisladas y el SIAGIE, lo que genera duplicidad, demoras y poca trazabilidad.

    El proyecto Plataforma Académica Distribuida (PAD) propone una solución web basada en microservicios, adaptada a la realidad de una institución educativa pública peruana y a la normativa del Ministerio de Educación (MINEDU). El sistema implementado está compuesto por siete microservicios de dominio desarrollados con Java 17 y Spring Boot 3.4 (Estudiantes, Cursos, Evaluaciones, Disciplina, Reportes, Notificaciones y Horarios), un API Gateway con Spring Cloud Gateway que centraliza la seguridad JWT, la resiliencia y los eventos en tiempo real, un intermediario de mensajería RabbitMQ y una instancia PostgreSQL 15 que aloja siete bases de datos independientes, una por servicio (database-per-service). La interfaz web fue construida con Angular 21 y se sirve mediante Nginx.

    Todo el sistema se ejecuta con Docker Compose en once contenedores con verificación de salud (health checks). La interfaz está diferenciada para once roles institucionales —Director, Administrador del sistema, Coordinación académica, Coordinación de convivencia, Secretaría, Docente, Auxiliar, Psicología, Enfermería, Mantenimiento y Apoderado— y aplica separación de funciones y mínimo privilegio.

    Este informe documenta el alcance funcional, la arquitectura, el modelo de datos distribuido y la implementación, e incluye evidencias reales obtenidas el 13 de octubre de 2026 sobre el sistema en ejecución: capturas de cada módulo, el estado de los contenedores, la mensajería y los resultados de las pruebas automatizadas de backend, frontend, humo (smoke) y contrato del gateway.

    Por tratarse del proyecto integrador de los cursos de Sistemas Distribuidos, Arquitectura de Software y Gestión de Base de Datos, cada decisión se explica desde esas tres perspectivas. Desde Sistemas Distribuidos se analizan la comunicación entre procesos, la tolerancia a fallos, la consistencia, la idempotencia y la observabilidad (apartado 2.2.7). Desde Arquitectura de Software se justifican el estilo arquitectónico, los patrones, las vistas del modelo 4+1, los atributos de calidad y las decisiones de diseño con sus alternativas (apartado 2.2.8). Desde Gestión de Base de Datos se fundamentan el modelo relacional, la normalización, la integridad, las transacciones, la concurrencia, las migraciones, la auditoría y la estrategia de respaldo y recuperación (apartado 3.1.6).     1. Descripción del Proyecto

    La Plataforma Académica Distribuida es un sistema web para la gestión académica y de convivencia de un colegio público de Educación Secundaria (I.E.P. Huamanga, institución de demostración), con datos de prueba de quince secciones de primero a quinto grado en turnos mañana y tarde, 500 estudiantes y 30 docentes. Automatiza la matrícula y la trayectoria del estudiante, la carga docente y los horarios, el ingreso al colegio con DNI, la asistencia, el registro de notas por competencias con la escala del Currículo Nacional (AD, A, B, C), la promoción de grado y la recuperación pedagógica, la convivencia escolar, la salud, el bienestar y las notificaciones a las familias.

    La distribución se realiza por dominios de negocio. Ningún servicio consulta directamente las tablas de otro; cuando necesita confirmar la carga académica de un docente, los datos de un estudiante o enviar una notificación, utiliza la API REST interna del servicio propietario, protegida además con una clave interna (INTERNAL_API_KEY). Los cambios relevantes se difunden en tiempo real a todas las pantallas abiertas mediante Server-Sent Events (SSE) emitidos por el gateway.

    1.1 Objetivos

    Objetivo general. Diseñar e implementar una plataforma académica distribuida para colegios públicos que gestione la matrícula, la carga docente y los horarios, la asistencia, las calificaciones por competencias, la convivencia y la comunicación con las familias mediante microservicios independientes, bases PostgreSQL aisladas, un API Gateway seguro, mensajería asíncrona y una interfaz web intuitiva que funcione en tiempo real.

    Objetivos específicos.

    1. Implementar autenticación sin estado con JWT y autorización por once roles institucionales, validada en el API Gateway y repetida en los servicios sensibles.
    2. Registrar la matrícula gratuita (nuevo ingreso, continuidad y traslado) conforme a la normativa del MINEDU, conservando la trayectoria del estudiante por año escolar.
    3. Gestionar niveles, grados, secciones, cursos, docentes, carga académica y horarios, con un generador de horarios parametrizable y editable, y reparto de un curso entre varios docentes.
    4. Registrar el ingreso al colegio escaneando el código de barras del DNI (lector USB o cámara), con detección automática de tardanzas.
    5. Registrar asistencia por sesión de clase y calificaciones por competencias con escala AD/A/B/C, incluido el dictado de notas por voz.
    6. Gestionar el cierre de bimestres, la promoción de grado, las áreas por subsanar y la recuperación pedagógica.
    7. Gestionar convivencia escolar, derivaciones psicológicas, fichas médicas, atenciones de tópico y tickets de mantenimiento.
    8. Notificar a las familias mediante el patrón Outbox y RabbitMQ con reintentos y cola de mensajes fallidos (DLQ).
    9. Proporcionar indicadores, alertas de deserción, auditoría con Hibernate Envers y reconciliación de integridad entre servicios.
    10. Contenerizar todo el sistema con Docker Compose y comprobarlo con pruebas automatizadas (Testcontainers, Vitest, smoke y contrato).

    1.2 Justificación

    El manejo manual de matrículas, asistencia y notas provoca duplicidad, pérdida de información y dificultad para obtener reportes oportunos para la UGEL y para las familias. Además, en una institución pública intervienen muchos actores con responsabilidades distintas: el Director no debe registrar notas, la Secretaría no debe ver fichas médicas y el docente solo debe acceder a sus secciones. Una plataforma web única con roles bien delimitados mejora el servicio, mientras que la arquitectura distribuida separa las responsabilidades técnicas y reduce el acoplamiento (Newman, 2021).

    El patrón database-per-service evita que un módulo modifique datos que no le pertenecen (Richardson, 2018): Estudiantes conserva la identidad, la matrícula y el bienestar; Cursos controla la estructura curricular y la carga; Evaluaciones es responsable de notas, asistencia y bimestres; Disciplina gestiona la convivencia; Notificaciones entrega los mensajes; Reportes consolida indicadores; y Horarios ejecuta la optimización de horarios. Si un servicio falla, el gateway responde con un mensaje controlado (circuit breaker) y el resto del colegio sigue funcionando.

    El sistema se adapta a la normativa vigente: la matrícula en instituciones públicas es gratuita y no puede condicionarse al pago de APAFA, uniformes o útiles; la calificación del Currículo Nacional de la Educación Básica (CNEB) usa la escala literal AD, A, B y C; y la RVM N.° 094-2020-MINEDU regula la promoción, la permanencia y la recuperación pedagógica (Ministerio de Educación del Perú [MINEDU], 2016, 2020). El proyecto integra además conceptos de sistemas distribuidos —APIs REST, mensajería, consistencia eventual, tolerancia a fallos y observabilidad (Kleppmann, 2017)— en un caso real y verificable.

    Reglas de negocio principales.

    • La matrícula en una institución pública es gratuita; no se condiciona a pagos de APAFA, uniformes, útiles ni exámenes. El único documento exigible es el DNI o el acta de nacimiento.
    • Un estudiante tiene una sola matrícula por año escolar; un traslado de salida cambia su situación a TRASLADADO y lo retira de las listas activas.
    • Un docente no puede tener dos clases a la misma hora, una sección no puede tener dos cursos en el mismo periodo y la carga semanal no puede superar las horas contratadas.
    • El docente solo lee y escribe datos de las secciones y cursos de su carga académica vigente, aunque conozca el identificador de otro recurso.
    • Un bimestre cerrado vuelve inmutables sus notas; solo el Director puede reabrirlo y debe registrar un motivo auditado.
    • El ingreso registrado después de la hora límite del turno se clasifica como tardanza; un mismo DNI no se registra dos veces el mismo día.
    • Un estudiante promovido puede llevar áreas por subsanar; las áreas en recuperación quedan pendientes hasta registrar su resultado.
    • Cada notificación se guarda primero en una tabla outbox dentro de la misma transacción del negocio; su envío se reintenta y, si se agota, pasa a la DLQ.

    2.2.1 Descripción Jerárquica

    La arquitectura se organiza en cinco niveles (ver Figura 2):

    2.2.5 Descripción del Middleware de Comunicaciones

    El middleware está compuesto por los siguientes mecanismos, todos implementados y en ejecución:

    • Spring Cloud Gateway (WebFlux): enrutamiento por prefijo (/api/estudiantes/**, /api/notas/**, /api/horarios/**, etc.), validación JWT, RBAC y CORS.
    • Resilience4j: un circuit breaker por ruta con límite de 25 s y respuesta de respaldo (/fallback/{servicio}), con tiempos de conexión de 3 s y de respuesta de 30 s. El frontend reintenta automáticamente una vez las lecturas fallidas (0/502/503/504).
    • Server-Sent Events: un filtro global del gateway detecta cada escritura exitosa (POST, PUT, PATCH o DELETE) y publica un evento de cambio en /api/tiempo-real, filtrado por la audiencia de cada rol; las pantallas abiertas recargan solo el módulo afectado.
    • REST interno: clientes RestClient/WebClient entre servicios, autenticados con INTERNAL_API_KEY y propagando el ID de correlación (X-Correlation-Id).
    • Patrón Outbox + RabbitMQ: Estudiantes, Evaluaciones y Disciplina guardan la notificación en notification_outbox en la misma transacción; un proceso programado la entrega a Notificaciones, que la publica en el intercambio pad.eventos, la consume desde pad.notificaciones y, si falla definitivamente, la deriva a pad.notificaciones.dlq.
    • Manejadores globales de errores que devuelven 4xx para solicitudes inválidas y 5xx solo para fallas reales, siempre en JSON.
    • Observabilidad: Actuator (health), Micrometer/Prometheus y trazas OpenTelemetry hacia Zipkin.

    2.2.7 Fundamentos de Sistemas Distribuidos Aplicados

    Un sistema distribuido es un conjunto de procesos autónomos que se comunican por una red y se presentan al usuario como un sistema único y coherente (Tanenbaum & van Steen, 2017). La plataforma cumple esa definición: once procesos independientes en contenedores colaboran por HTTP y AMQP, y el docente o la secretaria perciben una sola aplicación web. A continuación se explica cómo se resolvieron los problemas propios de esta clase de sistemas.

    Transparencia. El usuario no sabe en qué servicio vive cada dato (transparencia de ubicación): el navegador solo conoce /api/** y el gateway decide el destino por prefijo de ruta. Los servicios se ubican por nombre DNS dentro de Docker (servicio-cursos:8083), por lo que pueden moverse o replicarse sin cambiar el frontend. La transparencia de fallos es parcial y deliberada: si un servicio cae, el usuario recibe un mensaje claro en lugar de un error técnico.

    Comunicación síncrona y asíncrona. Se usa comunicación síncrona (solicitud-respuesta REST) cuando el usuario necesita la respuesta para continuar; por ejemplo, Evaluaciones consulta a Cursos si el docente tiene carga en una sección antes de aceptar una nota. Se usa comunicación asíncrona cuando la operación puede completarse después sin afectar al usuario: los avisos a las familias pasan por una tabla outbox y por RabbitMQ, desacoplando en el tiempo al emisor del receptor. El tiempo real se resuelve con Server-Sent Events, un canal unidireccional del servidor al navegador apropiado para notificar cambios.

    Consistencia y teorema CAP. Ante una partición de red, un sistema distribuido debe elegir entre consistencia y disponibilidad (Brewer, 2012). Dentro de cada base de datos se garantiza consistencia fuerte con transacciones ACID. Entre servicios se acepta consistencia eventual donde no compromete la operación: una notificación puede llegar segundos después, los indicadores del inicio se recalculan y las referencias lógicas entre bases se verifican periódicamente con la reconciliación de integridad del servicio Reportes. Para operaciones críticas, como registrar una nota, se prefiere la consistencia: si Cursos no puede confirmar la carga del docente, la operación se rechaza en lugar de aceptar un dato dudoso.

    Tolerancia a fallos. Se aplicaron varias tácticas complementarias: (a) límites de tiempo (conexión de 3 s, respuesta de 30 s y límite de 25 s por ruta en el gateway), para que una llamada lenta no bloquee hilos indefinidamente; (b) circuit breaker por servicio con ventana de 10 llamadas, umbral de fallo del 50 %, 10 s en estado abierto y 3 llamadas de prueba en estado semiabierto; al abrirse, el gateway responde de inmediato con un 503 controlado; (c) reintento automático de lecturas en el frontend ante errores 0, 502, 503 o 504; (d) reintentos con espera exponencial en la outbox (2n segundos, máximo 300 s) hasta 10 intentos, y (e) cola de mensajes fallidos (DLQ) en RabbitMQ para no perder mensajes envenenados. La prueba de resiliencia del Anexo B5 lo demuestra: al detener Cursos el resto del sistema siguió atendiendo y el servicio se reincorporó solo al reiniciarse.

    Atomicidad sin transacciones distribuidas. En lugar de un protocolo de confirmación en dos fases (2PC), costoso y bloqueante, se usó el patrón Transactional Outbox: el cambio de negocio y el mensaje pendiente se guardan en la misma transacción local, y un proceso programado cada 5 s publica los pendientes. Así se evita el «doble escritura» inconsistente (guardar el dato pero perder el aviso, o avisar algo que no se guardó).

    Idempotencia y entrega al menos una vez. Como un mensaje puede reintentarse, el receptor debe tolerar duplicados. Cada evento lleva un evento_id único y la base de Notificaciones impone UNIQUE (evento_id, canal), por lo que un reintento no genera un segundo SMS. Del mismo modo, UNIQUE (estudiante_id, fecha) en ingresos_colegio impide registrar dos veces el mismo DNI en el día aunque dos lectores lo escaneen simultáneamente.

    Tiempo y concurrencia. En un sistema distribuido no se puede confiar en el reloj del cliente. La hora de ingreso y la tardanza se calculan en el servidor con la zona horaria America/Lima. Para cambios concurrentes sobre el estado de un bimestre se usa control optimista con un campo version: si dos coordinadores lo modifican a la vez, el segundo recibe un conflicto en lugar de sobrescribir.

    Escalabilidad y observabilidad. Los servicios no guardan sesión (JWT sin estado), por lo que pueden ejecutarse varias réplicas detrás del gateway. Cada solicitud recibe un X-Correlation-Id que se propaga entre servicios y aparece en registros, notificaciones y trazas de Zipkin, lo que permite reconstruir una operación que atravesó varios procesos.     3.1.6 Gestión de la Base de Datos

    Esta sección fundamenta el diseño de datos desde la disciplina de gestión de bases de datos (Elmasri & Navathe, 2016; Silberschatz et al., 2020). Las cifras se obtuvieron consultando el catálogo de PostgreSQL (pg_constraint, pg_indexes) de las bases en ejecución.

    Modelo relacional y normalización. Las tablas están en tercera forma normal: cada atributo depende solo de la clave primaria. Por ejemplo, los datos del apoderado no se repiten en cada estudiante; la relación muchos a muchos se resuelve con la tabla puente apoderado_estudiante, que además guarda atributos propios de la relación (parentesco y permiso de retiro). La matrícula se separa del estudiante (matriculas, una fila por año) para conservar la trayectoria histórica en lugar de sobrescribirla. Se aceptaron dos desnormalizaciones controladas: areas_pendientes.curso_nombre guarda el nombre del área tal como era en el año de origen (una «fotografía» histórica que no debe cambiar si luego se renombra el curso) y la base de Horarios mantiene una réplica de lectura del catálogo académico para que el motor de optimización trabaje sin consultar a otro servicio.

    Índices y rendimiento. Se crearon índices sobre las columnas usadas en filtros y uniones frecuentes: idx_nota_estudiante, idx_nota_curso, idx_asistencia_fecha, idx_sesion_seccion_fecha o el índice de mensajes pendientes de la outbox. También se usan índices parciales, como uk_usuario_apoderado ... WHERE apoderado_id IS NOT NULL, que garantizan unicidad solo cuando el valor existe. Los listados se paginan en la base (LIMIT/OFFSET mediante Pageable) para no transferir miles de filas.

    Transacciones y aislamiento. Las operaciones de negocio se delimitan con @Transactional (69 métodos en los servicios) y cumplen las propiedades ACID. Se usa el nivel de aislamiento READ COMMITTED de PostgreSQL, suficiente porque las situaciones de carrera relevantes se controlan con restricciones únicas y con control optimista. Un ejemplo de atomicidad es el guardado de horarios: todas las secciones de un turno se reemplazan en una sola transacción; si un bloque genera un cruce de docente, se revierte el lote completo y la base nunca queda con un horario a medias.

    Control de concurrencia. Se aplica control optimista mediante el campo version (anotación @Version de JPA) en bimestres_estado: la actualización incluye la versión leída y falla si otro usuario la cambió antes. Para las inserciones concurrentes (dos lectores de DNI a la vez, dos reintentos del mismo evento) la protección la dan las restricciones UNIQUE, que la base evalúa de forma atómica.

    Evolución del esquema. El esquema se versiona con 25 migraciones Flyway (V1__...sql a V8__...sql) que se aplican en orden al iniciar cada servicio y quedan registradas en flyway_schema_history con su suma de verificación. Hibernate trabaja con ddl-auto=validate: nunca altera el esquema, solo comprueba que coincida con las entidades. Así, el mismo esquema se reproduce exactamente en desarrollo, en pruebas (Testcontainers aplica las mismas migraciones) y en producción.

    Auditoría. Hibernate Envers registra cada cambio de estudiantes, apoderados y documentos en las tablas estudiantes_aud, apoderados_aud y documentos_aud, con el número de revisión, la fecha, el actor y el ID de correlación (revinfo). Los bimestres llevan su propia bitácora (bimestres_auditoria) con el motivo de cada cierre o reapertura.

    Seguridad y privacidad de los datos. Las credenciales de la base se inyectan por variables de entorno y no se versionan; PostgreSQL solo escucha en 127.0.0.1 fuera de Docker. Las contraseñas de usuarios se guardan con BCrypt. Los datos sensibles de salud y bienestar están en tablas a las que solo acceden Enfermería y Psicología, y las autorizaciones de tratamiento de datos se registran en consentimientos_datos con versión de la política y evidencia, conforme a la Ley N.° 29733 de Protección de Datos Personales.

    Respaldo y recuperación. El servicio backup-postgres (perfil operations) ejecuta pg_dump en formato personalizado de cada base, cifra el archivo con AES-256 (OpenSSL con PBKDF2 de 200 000 iteraciones), lo repite cada 24 horas y conserva 30 días de copias (configurable entre 7 y 365). El script verify-restore.sh restaura la última copia en una base temporal para comprobar que realmente se puede recuperar, y ops/tests/backup-restore.ps1 automatiza esa verificación. La persistencia ante reinicios se comprobó en el Anexo B6.

    Conexiones. Cada servicio usa un pool HikariCP (hasta 15 conexiones en Cursos y Horarios, 10 por defecto en los demás); la suma (≈ 80) queda por debajo del límite max_connections = 100 de la instancia, dejando margen para el respaldo y la administración.

    @Component
public class CambiosGlobalFilter implements GlobalFilter, Ordered {
    public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {
        HttpMethod metodo = exchange.getRequest().getMethod();
        if (!ESCRITURAS.contains(metodo)) return chain.filter(exchange);
        return chain.filter(exchange).then(Mono.fromRunnable(() -> {
            HttpStatusCode estado = exchange.getResponse().getStatusCode();
            if (estado != null && estado.is2xxSuccessful()) {
                tiempoReal.publicar(exchange.getRequest().getPath().value(), metodo, usuario(exchange));
            }
        }));
    }
}

    Conclusiones

    Desde Sistemas Distribuidos

    1. La plataforma funciona como un sistema distribuido real: once procesos independientes se comunican por HTTP y AMQP y se presentan al usuario como una sola aplicación, gracias a la transparencia que aporta el API Gateway.
    2. La combinación de límites de tiempo, circuit breaker, reintentos con espera exponencial y DLQ evita los fallos en cascada; la prueba de resiliencia demostró que la caída de un servicio no detiene al resto.
    3. El patrón Outbox con entrega idempotente sustituye a las transacciones distribuidas: garantiza que ningún aviso se pierda ni se duplique, aceptando consistencia eventual solo donde no afecta la operación.

    Desde Arquitectura de Software

    1. Dividir el sistema por contextos del dominio escolar produjo servicios cohesivos y poco acoplados, lo que permitió agregar matrícula por tipos, ingreso con DNI, promoción y recuperación sin modificar los demás servicios.
    2. Los patrones API Gateway, Database per Service, Outbox y Circuit Breaker, documentados con las vistas 4+1 y un registro de decisiones, hacen explícitos los compromisos asumidos (por ejemplo, una sola instancia de PostgreSQL a cambio de menor costo).
    3. Los atributos de calidad priorizados para un colegio público —seguridad, disponibilidad en la hora de ingreso, usabilidad y mantenibilidad— se tradujeron en tácticas concretas y verificables con 64 pruebas de backend, 36 de frontend, 50 de humo y 10 de contrato.

    Desde Gestión de Base de Datos

    1. Las siete bases normalizadas, con 55 claves primarias, 32 foráneas, 24 restricciones únicas y 19 CHECK, llevan las reglas del colegio al nivel de la base, de modo que ni un error de código ni dos operaciones simultáneas pueden dejar datos inválidos.
    2. Las transacciones ACID, el control optimista y las migraciones Flyway con validación del esquema garantizan integridad y reproducibilidad; la auditoría con Envers y la bitácora de bimestres dan trazabilidad de quién cambió qué.
    3. Los respaldos cifrados con restauración verificada y la persistencia comprobada ante reinicios aseguran que la información académica de los estudiantes pueda recuperarse ante un incidente.
